# Trikey mobile app

The phone app: key 2 of the 2-of-3 wallet. React Native with Expo SDK 58 and expo-router.

## Running it

```sh
npm install                      # at the repository root
npm run web -w @trikey/mobile    # browser preview: UI only, see "On web" below
```

The phone features (secure key storage, iCloud and Google Drive backup, passkeys) are native
modules, so they **do not run in Expo Go**. Use a development build:

```sh
npx expo run:ios        # needs macOS and Xcode; run from apps/mobile
npx expo run:android    # needs the Android SDK
npx expo start --dev-client
```

`ios/` and `android/` are generated by `expo prebuild` and are git-ignored.

```sh
npm test -w @trikey/mobile        # unit tests (vitest)
npm run typecheck -w @trikey/mobile
```

## Wallet modes

The screens run on one of three wallets, chosen at startup and remembered on the phone. Switch in
**Settings, Developer, Wallet mode** (a confirmation first; nothing is deleted, each mode keeps its own wallet
and data) or from the small "wallet mode" link on the first screen.

| Mode | What is behind the screens | Default |
|---|---|---|
| **Demo** | Sample data and timers (`src/data/mock.ts`) | development builds and the web |
| **Simulator** | The real wallet with a software "hardware wallet" and throwaway keys, on regtest: guardian mode (`src/data/real.ts` on `@trikey/wallet`) against a guardian you run on your computer, Recovery Key mode (`src/data/rk-service.ts` on `@trikey/recovery-key`) against the simulated chain from `npm run rk-sim` | |
| **Real** | The real wallet (either kind) with Ledger, Trezor and QR devices, this phone's secure storage and the network chosen at onboarding: testnet (the default), signet or regtest, or mainnet in guardian mode only, behind a pre-alpha warning the person accepts | release builds on a phone |

Real needs secure key storage, so the browser preview offers Demo and Simulator only. In the browser the simulator
keeps everything in memory (a reload starts over).

- Run a local backend for the simulator: [docs/dev-regtest.md](docs/dev-regtest.md). The quickest is
  `npm run dev-rig -w @trikey/mobile`: the real guardian, two relays and a fake Electrs in one process, no bitcoind.
- `npm run measure -w @trikey/mobile` times the expensive steps (wallet creation, pairing, a payment, the Argon2id of the
  recovery code) in Node, through the same code path the app uses.
- Guardian mode or Recovery Key mode ("No home server?" at onboarding) is chosen when the wallet is made: a phone runs one
  wallet of one kind per mode and network. Recovery Key mode is described below.

## Recovery Key mode

The wallet for people with no home server: the vault's third key is a printed Recovery Kit (or a second hardware wallet), and the
phone spends from a small balance that pre-signed, timelocked refills top up (`DESIGN.md`, "Recovery Key mode"). In the app:

- **Service.** `src/data/rk-service.ts` implements `WalletService` on `RecoveryKeyWallet`; what only this mode has is `service.rk`
  (`src/data/rk-actions.ts`: the kit, the refills, the vault, recovery with the kit, the chain server). `src/data/routed.ts` hands
  the screens whichever kind the phone runs. The demo's mock implements the same actions with sample data.
- **Screens.** `app/rk/*` (make the kit, approve refills, replace a lost kit), the Recovery Key home (`src/components/home-rk.tsx`),
  `app/recover/kit.tsx` (recover with a kit), Settings (chain server, refill amount).
- **The kit is never stored.** The page is handed to the OS print dialog (`expo-print`, `src/lib/print-kit.ts`), which also saves a
  PDF or sends it with AirDrop. The app writes no file of it: a copy in the app's own storage would sit next to the phone key.
  Printers, print queues and wherever a PDF goes may keep a copy, and the screen says so.
- **Chain server.** The default is a public Esplora (mempool.space on testnet4 and signet), which sees every address and the phone's
  IP address; Settings, Chain server takes your own (tried with a real request, and checked for the right network, before it is used).
- **Test networks only.** The app never passes `allowMainnet`; testnet, signet and regtest are offered (`RK_NETWORKS`). Mainnet
  is the guardian mode's only (`GUARDIAN_NETWORKS`): picking it at onboarding while this mode was chosen moves the phone back to
  the guardian mode.

### Refill scheduler

`runScheduler()` (sends the next refill when its timelock has passed and the spending balance is low; reports refills this phone did
not send, vault spends it did not make, stuck refills) runs:

- when the app opens, when it comes back to the front, on pull to refresh and every minute while it is open (`sync()` of the service);
- from a periodic background task on iOS and Android (`src/data/rk-background.native.ts`: `expo-background-task` on
  `expo-task-manager`, the replacement for `expo-background-fetch`). It needs no account: the config plugin only adds the
  `processing` background mode and a task identifier to Info.plist. The system decides when it runs (15 minutes at the soonest,
  on iOS often once or twice a day while charging), it does not run in Expo Go or the iOS Simulator, and on iOS the wallet's
  integrity key is only readable while the phone is unlocked, so a run on a locked phone ends quietly. Opening the app always runs
  the scheduler too. Not tried on a device yet; `npm test` runs the same code (`src/data/rk-background-run.ts`) against the
  simulated chain.

## Alpha without developer accounts

The alpha needs **no Apple Developer, Google Play or Google Cloud account**. What that takes away, and what replaces it:

| | Without accounts | Why |
|---|---|---|
| Passkeys | unavailable (`isSupported()` is false) | they need a domain you control and an app-association entry in your team |
| iCloud Drive and Google Drive backup | unavailable (`isAvailable()` is false), shown as "coming later" | they need the iCloud entitlement and a Google OAuth client |
| **Backup** | **a recovery code plus a backup file** | see below |

**Backup, step by step.** The backup step creates an encrypted backup file on the phone (the `file` provider) and shows a
**recovery code once**: write it on paper. "Save backup file" sends the file to the share sheet (Files, AirDrop, an email to
yourself). The file alone is useless without the code, and the code alone is useless without the file, so keep them apart.
To restore on a new phone, choose "Open a backup file" on the Restore screen, pick the file and type the code. Nothing leaves
the phone unless you send it.

### iOS (free Apple ID)

1. Xcode on a Mac, signed in with your Apple ID (Xcode, Settings, Accounts). A free account is enough.
2. Leave `EXPO_PUBLIC_PASSKEY_RP_ID` **unset** (it adds the Associated Domains capability, which a free account cannot sign) and
   build **without iCloud**: `TRIKEY_DISABLE_ICLOUD=1` (see `.env.example`). Nothing in the app or in `app.config.ts` then asks
   for the iCloud or associated-domains entitlements. Leave `TRIKEY_IOS_NFC` unset too: NFC (a Coldcard over NFC) needs the
   NFC Tag Reading capability, which a free account cannot sign; such a build has no NFC, and says so in its device list.
3. Build the app straight onto your phone (USB, or Wi-Fi after the first time). `--configuration Release` puts the
   JavaScript inside the app, so it opens without Metro running on your computer (leave it out for a development client
   that loads the JavaScript from `npx expo start --dev-client`):

   ```sh
   cd apps/mobile
   TRIKEY_DISABLE_ICLOUD=1 npx expo run:ios --device --configuration Release
   ```

   Pick your Apple ID as the team if Xcode asks, and trust the developer profile on the phone (Settings, General, VPN &
   Device Management). Set your own `TRIKEY_IOS_BUNDLE_ID` (a bundle id you can register for free, like
   `com.yourname.trikey`) if `app.trikey.wallet` is refused.
4. A free provisioning profile lasts **7 days**: after that the app stops opening until you run the same command again. The
   wallet's data stays on the phone, so a reinstall over it keeps your wallet, but make a backup first.

If the build fails, these are the snags met on a first build from a Mac (Xcode 26.6, iOS 26.6):

- **`pod install` fails with `Unicode Normalization not appropriate for ASCII-8BIT`**: CocoaPods needs a UTF-8 shell. Run
  `export LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8` first.
- **`No device UDID or name matching ...`**: `--device` wants the phone's name or its hardware UDID
  (`xcrun devicectl device info details --device <id>`, the `udid` field), not the CoreDevice identifier that
  `xcrun devicectl list devices` prints.
- **`iOS 26.5 is not installed. Please download and install the platform`**: install the iOS platform Xcode builds against
  (`xcodebuild -downloadPlatform iOS`, several GB), and don't start a second download from Xcode's Components pane meanwhile.
- **`No profiles for '<bundle id>' were found`** on the first build for a new bundle id: `expo run:ios` doesn't let Xcode create
  a profile. Open `ios/Trikey.xcworkspace` in Xcode once, pick your Personal Team under Signing & Capabilities so Xcode makes
  the profile, then run the command again.
- **`No available simulator runtimes for platform iphonesimulator`** while compiling asset catalogs (even for a device build): the
  simulator runtime is installed but not mounted (`xcrun simctl list runtimes` is empty). Quit Xcode and run
  `sudo killall simdiskimaged`; check that `xcrun simctl list runtimes` lists it, then build again.
- **The first run ends with `Unable to launch ... profile has not been explicitly trusted`**: the app is installed. Trust your
  developer profile on the phone (Settings, General, VPN & Device Management; the entry appears once an app signed with your
  Apple ID is on the phone) and open Trikey from the home screen.

CI builds the same Release app for the iOS Simulator (no signing, no Apple account) and opens it in a simulator on every pull
request that touches the app: `.github/workflows/ios-launch.yml` fails if the app is not running 25 seconds later or crashed,
with the crash report and log lines in the check's annotations.

### Android

```sh
cd apps/mobile
npx expo run:android            # a connected phone or an emulator (debug build)
# or a locally built APK to hand to testers:
npx expo prebuild --platform android && (cd android && ./gradlew assembleRelease)
# the same without Google code (see "Two Android builds" below):
export TRIKEY_ANDROID_VARIANT=foss
npx expo prebuild --platform android --clean && (cd android && ./gradlew assembleRelease)
```

A debug or locally signed build installs without any store account. (Google Drive backup stays "coming later"; the backup file
works as on iOS.)

### Two Android builds

The Android app comes in two builds from the same code, chosen with `TRIKEY_ANDROID_VARIANT` when the
native project is generated and built (`android-variant.js` has the details):

| | `standard` (the default) | `foss` |
|---|---|---|
| Release APK | `trikey-alpha-v<version>.apk` | `trikey-alpha-foss-v<version>.apk` |
| Google code | Google Sign-In, Google's ML Kit (QR codes), the Google Play services passkey provider | none: the build fails if any is in the APK |
| QR codes read by | ML Kit, through `expo-camera` | zxing-cpp (open source), through the app's own camera module, `modules/trikey-qr-camera` (CameraX) |
| Google Drive backup | when `EXPO_PUBLIC_GOOGLE_OAUTH_CLIENT_ID` is set (needs Google Play services on the phone) | never offered; the backup is the recovery code plus the backup file, which the share sheet can still put in Google Drive |
| Passkeys | `androidx.credentials` with the Play services provider (when `EXPO_PUBLIC_PASSKEY_RP_ID` is set) | `androidx.credentials` without it: only other credential providers, on Android 14 and later |
| Settings → About | Trikey | Trikey (no Google) |

Both have the same package name and are signed with the same release key, so either installs over the other and the wallet
stays. Check for updates (Settings → About) offers the APK of the build that is installed. iOS has one build.

How the FOSS build leaves Google out:

- **Native linking.** `react-native.config.js` turns off Android linking of `@react-native-google-signin/google-signin` and
  `react-native-cloud-storage` (on Android it is only Google Drive). The config plugin `plugins/with-android-variant.js` writes
  the Expo modules to leave out into `settings.gradle` (`expo-camera` for FOSS, whose Kotlin code refers to ML Kit even with
  its scanner off; the app's own `trikey-qr-camera` for standard) and excludes `androidx.credentials:credentials-play-services-auth`
  from the app's dependencies (`androidx.credentials` stays).
- **JavaScript.** Metro bundles `name.android.foss.ts(x)` in place of `name.ts(x)`: the camera (`src/hardware/ui/qr-camera`),
  the native module loaders (`src/platform/native-modules`) and the build's name (`src/lib/android-variant`). Importing any of
  the left-out packages from the FOSS Android bundle is a build error, so the app cannot crash on a missing native module.
- **The check.** CI scans the FOSS APK (`scripts/apk-google-scan.mts`): any class or mention of `com/google/android/gms`,
  `com/google/firebase`, `com/google/mlkit` or `com/google/android/datatransport` in its dex files, ML Kit's `libbarhopper`,
  or Google's version files or manifest entries fail the build. Run it on any APK:
  `node --import tsx apps/mobile/scripts/apk-google-scan.mts <app.apk> --require-none` (from the repository root).
- **The same value everywhere.** Linking, the bundle and the app config read `TRIKEY_ANDROID_VARIANT` again during the Gradle
  build, so set it for both `expo prebuild` and `gradlew` (the generated project stops if they differ), and start Metro with
  `--clear` after switching. `src/hardware/ui/qr-decoding.test.ts` runs the FOSS decoder's options (zxing-cpp as WebAssembly)
  on camera-like frames of every code the app scans.

### The demo walk (Maestro)

After the launch check, CI walks through the demo on both platforms with [Maestro](https://maestro.dev): from the first
screen into Demo mode, Home and its balance, Send to the amount screen, Receive, Settings and Activity, back to Home each
time, so a screen that crashes or shows nothing when it is opened fails the pull request
(`.maestro/demo-walk.yaml`; the failing step, Maestro's error and the app's log lines are in the check's annotations, the
screenshots in the `android-demo-walk-<variant>` / `ios-demo-walk` artifact; Android walks both builds). To run it yourself, install the Maestro CLI
(`.github/scripts/install-maestro.sh` installs the version CI uses; it needs Java 17), start an Android emulator or an iOS
Simulator with the app installed (a Release build starts on Welcome in Real mode, a debug build in Demo; the flow handles
both), and from the repository root run `maestro test apps/mobile/.maestro/demo-walk.yaml` (add `--device <id>` when more
than one is running). The flow taps accessibility labels and a few `testID`s (`welcome-change-mode`, `home-balance`,
`home-see-all`, `receive-address`, `screen-back`): keep them when you change those screens, or update the flow with them.

## Platform layer: `src/platform/`

`createPlatform()` returns what `@trikey/wallet` needs from the phone (the interfaces are in
`packages/wallet/src/platform.ts`). Each piece also has an `isSecure` flag.

| Piece | iOS and Android | Web (preview only) |
|---|---|---|
| `SecureKeyStore` | `expo-secure-store`: Keychain / Android Keystore, behind Face ID or fingerprint, this device only | in memory, `isSecure: false` |
| `KeyValueStore` | `expo-sqlite` key-value store (non-secret data only) | `localStorage`, `isSecure: false` |
| `CloudBackupStore` | iCloud Drive (iOS), Google Drive `appDataFolder` (Android, standard build only), and a local `file` provider | in memory, `isSecure: false` |
| `PasskeyPrf` | `react-native-passkey`: WebAuthn PRF, iOS 18+ and Android Credential Manager | always unsupported |

Notes on the choices:

- **Secure keys.** Items are `WHEN_UNLOCKED_THIS_DEVICE_ONLY`: never in iCloud Keychain, never in
  device backups. When biometrics change, iOS and Android make the key unreadable and
  `expo-secure-store` answers `null`, the same as "no such key". The store writes a small non-secret
  marker next to the seed so it can tell the two apart and throw `biometrics-changed`. Errors are
  `SecureKeyError`s with a `code` (`cancelled`, `no-biometrics`, `biometrics-changed`, `lockout`, ...) and
  a `userMessage` the UI can show. In the iOS Simulator, enable Features > Face ID > Enrolled first, or
  saving behind biometrics fails with `no-biometrics`.
- **Key-value store.** `expo-sqlite/kv-store` over AsyncStorage: it ships with the SDK (no extra native
  dependency or Gradle repository to configure), writes are SQLite transactions, and it has no 6 MB cap.
  The API is the same shape, so it can be swapped.
- **Cloud backup.** Provider through `react-native-cloud-storage` 3.x, which has native iCloud and
  Google Drive support, binary files, an Expo config plugin and works in development builds. Every
  `write` is read back and compared (`verify-failed` if different). Names are restricted to
  `[A-Za-z0-9._-]`. Google Drive needs a sign-in: `isAvailable()` never shows UI, `connect()` or the
  first `read`/`write` does.
- **Passkeys.** `react-native-passkey` 3.3+ supports PRF on iOS 18+ and Android. It needs a domain you
  control; see [docs/passkeys.md](docs/passkeys.md).
- **Polyfills.** `index.ts` (the entry) loads `src/platform/polyfills.ts` first. It installs
  `crypto.getRandomValues` (backed by `expo-crypto`, the OS random generator), `crypto.randomUUID`, and
  `TextEncoder`/`TextDecoder` if Hermes lacks them, then pins that `getRandomValues` as the one source of every key
  and secret (`secureRandomBytes` in `@trikey/core/random` refuses to run if it is replaced later). The Ledger kit's
  `react-native-get-random-values` finds it already installed and installs nothing; `src/hardware/common/random.native.ts`
  checks that. `WebSocket` (nostr-tools) comes from React Native. See DESIGN.md, "Entropy".
- **Metro.** `metro.config.js` resolves `./file.js` imports to `./file.ts`, because the workspace
  packages are TypeScript sources written that way, and swaps in the `.android.foss.ts(x)` files of the Android build
  without Google code ("Two Android builds").

### Self-test

In a development build, Settings > Developer > **Crypto self-test** runs BIP39/BIP32 key derivation, a
BIP48 multisig address, NIP-44 encryption and a NIP-59 gift wrap through `@trikey/core` and
`@trikey/protocol` on the device, and shows pass or fail. The same test runs in Node as part of
`npm test`.

### On web

The browser preview runs the UI against in-memory stand-ins. Nothing there is protected: the "secure"
store is a JS variable and the backup disappears on reload. Do not use it with real funds. Check
`platform.isSecure` before offering to hold any.

## Publishing your own build

The repository contains no accounts, keys or domains. Whoever publishes a build supplies their own.
Configuration comes from the environment; copy `.env.example` to `.env` (git-ignored) or set the
variables in your build service (for example EAS secrets).

| Variable | What it is | If unset |
|---|---|---|
| `TRIKEY_IOS_BUNDLE_ID` | Your iOS bundle identifier | `app.trikey.wallet` from `app.json` (the Trikey project's own, you cannot sign it) |
| `TRIKEY_ANDROID_PACKAGE` | Your Android package name | `app.trikey.wallet` from `app.json` |
| `TRIKEY_APPLE_TEAM_ID` | Your Apple Team ID | Xcode asks |
| `TRIKEY_ICLOUD_CONTAINER` | `iCloud.<your bundle id>` | `iCloud.<bundle id>` |
| `TRIKEY_ICLOUD_ENVIRONMENT` | `Development` or `Production` | `Production` |
| `TRIKEY_DISABLE_ICLOUD` | `1` builds without iCloud | iCloud on |
| `TRIKEY_IOS_NFC` | `1` builds iOS with NFC (a Coldcard Mk4 or Q over NFC); needs the NFC Tag Reading capability (paid account) | No NFC on iOS (Android always has it) |
| `TRIKEY_ANDROID_VARIANT` | `standard` or `foss` (no Google code); set it for both the prebuild and the Gradle build | `standard` |
| `EXPO_PUBLIC_GOOGLE_OAUTH_CLIENT_ID` | Google OAuth client ID (Android backup) | Google Drive backup unavailable |
| `EXPO_PUBLIC_PASSKEY_RP_ID` | Passkey domain: `trikey.app` for the project's builds, your own domain for a fork | Passkeys unsupported |

`EXPO_PUBLIC_` values are compiled into the app. They are identifiers, not secrets.

### iOS

1. In your Apple Developer account, register an App ID for your bundle identifier with the
   **iCloud** (iCloud Documents) and **Associated Domains** capabilities.
2. Create an iCloud container named `iCloud.<your bundle id>` and set `TRIKEY_ICLOUD_CONTAINER` to it.
   `app.config.ts` adds the container entitlements and `NSUbiquitousContainers` through the
   `react-native-cloud-storage` config plugin.
3. Set `TRIKEY_APPLE_TEAM_ID`. Without a paid account iCloud is unavailable: build with
   `TRIKEY_DISABLE_ICLOUD=1` and the backup falls back to the local `file` provider.
4. For passkeys: host `apple-app-site-association` as described in [docs/passkeys.md](docs/passkeys.md) and
   set `EXPO_PUBLIC_PASSKEY_RP_ID`. `app.config.ts` then adds the `webcredentials:<domain>` associated domain.
5. `NSFaceIDUsageDescription` is set by the `expo-secure-store` plugin (text in `app.json`).
6. For NFC (a Coldcard Mk4 or Q over NFC): turn on **NFC Tag Reading** for the App ID and build with
   `TRIKEY_IOS_NFC=1`. `plugins/with-ios-nfc.js` then adds `com.apple.developer.nfc.readersession.formats` (`TAG`) and
   `NFCReaderUsageDescription`, and react-native-nfc-manager is linked on iOS (`react-native.config.js`, `ios-nfc.js`).
   Without it the iOS build has no NFC code at all. Android needs nothing: the library's manifest asks for the NFC
   permission and declares NFC not required, so phones without it still install the app.

### Android

1. Choose your package name (`TRIKEY_ANDROID_PACKAGE`).
2. Google Cloud console, one project:
   - enable the **Google Drive API**;
   - configure the OAuth consent screen and add the scope `https://www.googleapis.com/auth/drive.appdata`
     (the app's hidden data folder; it cannot see the rest of the user's Drive);
   - create an **Android** OAuth client with your package name and the SHA-1 of your signing key (debug
     keystore for development builds, your upload or Play app-signing key for releases);
   - create a **Web application** OAuth client and put its client ID in
     `EXPO_PUBLIC_GOOGLE_OAUTH_CLIENT_ID`.
3. For passkeys: host `assetlinks.json` as described in [docs/passkeys.md](docs/passkeys.md) with your
   package name and signing-key SHA-256, and set `EXPO_PUBLIC_PASSKEY_RP_ID`.

### Before you ship

Backups and passkeys are tied to the identifiers above. Changing the passkey domain, the iCloud
container or the Google project later orphans existing backups. Choose them once.
